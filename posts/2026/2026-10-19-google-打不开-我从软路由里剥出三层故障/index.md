## 我为什么要做这件事

那天想查个资料，Google 死活打不开。不是慢——是彻底连不上。转手开百度，秒开。

家里网络是软路由管的，境外流量走 OpenClash。第一反应：订阅挂了？可我一直觉得这份订阅是好的，不该这么快就死。

事实证明，直觉只对了一半——这次故障足足有三层，一层比一层藏得深。

## 动手之前

- 一台 iStoreOS 软路由（22.03.6），装着 OpenClash，内核是 Mihomo (Meta)，后台在 192.168.100.1
- 机场订阅一份（事后证明它确实是好的，只是没启用）
- 这次排查的方式有点特别：我没自己一个个点页面，而是让 Claude Code 通过浏览器替我操作后台——我负责登录和拍板，它负责翻状态、看日志、跑验证。下面写的是它实际走过的路，每一步都验证过

## 具体怎么做

### 第一步：先分层，别急着改设置

修网络最容易犯的错，是一进后台就到处乱点。先做分层测试：

百度打开——秒开。说明宽带、路由、DHCP 全都没事，问题锁死在代理这一层。

顺带看了一眼运行状态：**运行模式被切在了「直连」上**。等于防弹衣穿上了，包装都没拆。什么时候被切过去的已经不可考，切回「规则」，Google 还是打不开。继续剥。

### 第二层：93 个节点，全部 503

打开控制面板，对着节点列表点了一圈延迟测试：**93 个节点，全部 503**，一个活的都没有。

503 一般意味着节点全死，十有八九是订阅过期。翻出订阅信息一看，正在跑的这份配置来自一家 **8 月 13 号就到期**的机场——也就是说，路由器上跑了两个多月的死配置。

讽刺的是，有效的新订阅其实已经躺在配置列表里了，之前导入过，只是一直没切换启用。

操作：更新新订阅 → 配置列表里切换过去 → 重启核心。再测延迟：96ms、116ms、59ms，全活了。

到这一步，按剧本 Google 该通了。

它没通。而且报错变了：从「连接被切断」变成了 **ERR_NAME_NOT_RESOLVED**——域名解析不了。

这个变化就是关键线索：**节点通了，现在卡在 DNS 上。**

### 第三层：日志里藏着真凶

网页报错是给人看的安慰剂，路由器里还有一份内核日志。翻到「内核日志」标签，满屏都是同一句：

`dns resolve failed: couldn't find ip`

实锤了。但为什么解析不了？上路由器的网页终端（iStoreOS 自带，7681 端口），直接看 OpenClash 正在跑的配置：

```yaml
proxy-server-nameserver:
  - udp://127.0.0.1:1053
```

解释一下这行是什么：`proxy-server-nameserver` 是 Mihomo 里专门给「节点服务器自己的域名」用的 DNS。节点地址如果不是纯 IP 而是域名，核心得先把它解析成 IP 才连得上——用的就是这个列表。

而这条配置指向本机的 1053 端口。查了一圈：**路由器上没有任何进程在监听 1053**。

这是很多机场配置文件的通病：模板是给「装了全套 DNS 分流服务」的机器写的，默认你本地跑着一个监听 1053 的 DNS 服务（某些一键脚本会装）。你的机器上没有，这条配置就成了黑洞——所有节点域名解析全部掉进去，全网 503。

所以真相是两层的：**旧订阅死了 + 配置里藏着死 DNS**。就算早两步切到新订阅，照样瘫着。

### 不硬改文件，走正规机制

第一个念头是直接把 yaml 里那行删了。不行——这个文件是每次更新订阅时重新生成的，手改了，下次更新又给覆盖回去。

OpenClash 留了正规入口，在插件的 DNS 设置里：

1. 勾上「**自定义上游 DNS**」，里面预置了 114.114.114.114、119.29.29.29 这类国内 DNS；
2. 给每一条 DNS 条目勾上「**用于节点解析**」——这个开关藏得深，勾了之后这些 DNS 会被合并进 `proxy-server-nameserver`，把死端口顶掉。

重启核心，上终端验证：

```bash
grep -A5 proxy-server-nameserver /etc/openclash/*.yaml
# 输出里 127.0.0.1:1053 没了，114 和 119 都在
```

节点全部满血。三层剥完。

### 还差最后半层

节点活了，Google 却还是打不开，报错依旧是域名解析失败。这回轮到 **google.com 自己**解析不出来。

原因在解析模式：当前是 redir-host，判定为境外的域名不走国内 DNS，走 fallback 组的 DoH——而列表里是 dns.google 和 Cloudflare 的 DoH，**它们自己就需要代理才能访问**。DNS 不通，浏览器连域名都拿不到；可 DNS 要通，又得先有代理。先有鸡还是先有蛋。

破局的开关就在运行状态页：「**DNS 代理**」（respect-rules）——让 DNS 查询本身也按代理规则走。打开，齐活。

最终验证：Google 搜索正常出结果，YouTube 正常播放，百度不受影响。

## 我踩到的坑

**坑一：503 会骗人。**
现象：全节点 503，直觉就是「订阅过期」。
原因：这次是「订阅过期」和「DNS 死上游」叠加。
解决：别只盯着订阅，内核日志里的 `dns resolve failed` 才是实锤。503 只说明核心连不上节点，不说明为什么连不上。

**坑二：手改配置文件的冲动。**
现象：想直接删 yaml 里那行死 DNS，一秒就能改完。
原因：运行配置每次更新订阅都会重新生成，手改必被覆盖。
解决：走 OpenClash 的设置开关（自定义上游 DNS + 用于节点解析），让它每次生成时自动合并，一劳永逸。

**坑三：钩子脚本静默失败。**
现象：先试了 OpenClash 的自定义脚本钩子去覆盖 DNS 配置，改完毫无反应，也不报错。
解决：放弃这条路，改用上面那两个可视化开关。教训：内部钩子调用失败了不吭声，能走正规开关就走正规开关。

## 结果与花费

钱：0 元。订阅是现成的，所有开关都是现成的，路由器上总共只跑了一条 grep。

时间：从「打不开」到三层剥完，是一场连续排查，中间没有重启路由器，家里网络没断过。

## 小结

1. 修网络先分层：国内通不通、代理通不通、DNS 通不通，一层一层锁，别上来就乱点设置。
2. 「全节点 503」有两个嫌疑人：订阅死了，或者核心解析节点域名的 DNS 死了。网页报错会说谎，内核日志不会。
3. 机场配置文件别全信——它假设你机器上跑着它的配套服务。凡是指向 127.0.0.1 某个端口的配置，先查有没有人监听。
