## 我为什么整理这份命令清单

第一次打开 Claude Code 的时候，我输入了一个 `/`。

然后屏幕上刷出来一整列命令：/init、/compact、/context、/rewind、/agents、/mcp……几十条，每条后面还跟着参数说明。说实话，那一刻我根本不知道该用哪个，索性当它不存在，直接打字聊天。

用了两天回头看，这个做法歪打正着：这几十条命令里，真正天天用的就十来条，剩下的要么是特定场景的救火工具，要么等我以后有了更复杂的需求再说。

这篇文章就是我这几天的清单——一个刚上手 Claude Code 的新手，按软件工程的老规矩（先设计、再动手、发布前过质量关）整理出真正常用的部分。

## 动手之前

前置条件很简单：装好 Claude Code，能启动，能对话。我是用中转站接的 API，配置过程写在上一篇《在 Windows 上用 Claude Code：用 cc-switch 接中转站，把订阅阻力降到最低》里，这里不重复。

另外先分清一件事，Claude Code 的命令分两类：

- **内置命令**：装完就有，/init、/clear 这些，本文讲的全是这类
- **自定义命令**：自己写的 md 文件，把你的流程固化成一条 /命令，文末进阶部分讲

内置命令的完整清单在官方文档里，大几十条。本文不搬运清单，只挑我真正用上的。

## 第一次开工：把项目交给 Claude

拿到一个新项目，我的固定动作是三条命令。

![](assets/3.png)

**/init** —— Claude Code 会扫描整个仓库，生成一个 CLAUDE.md 文件。这东西相当于给新同事写的 onboarding 文档：项目是干什么的、目录怎么组织、用什么命令跑测试、有哪些约定。以后每次启动对话，Claude 都先读它。

我的用法：CLAUDE.md 写得越像「给同事的交代」，Claude 干活越不用反复纠正。项目约定、常用命令、禁忌，都往里放；但别写成小说，几屏以内。

**/memory** —— 随时打开编辑 CLAUDE.md。用着用着发现 Claude 总犯同一个错，别每次口头纠正，把规矩写进去，一次搞定。

**/permissions** —— 配置哪些操作不用每次弹窗批准，比如放行所有 git status、禁掉危险命令。刚上手可以不管，等弹窗烦了再配。

## 日常循环：一个任务从开始到收工

这是每天真正在用的部分，我按一个任务的生命周期排。

![](assets/2.png)

**/plan —— 动手之前先要方案。** 后面跟一句任务描述，Claude 进入计划模式：先读代码、出方案，你批准了才动编辑器。改两三个文件的活我直接让它干；要动十几个文件的伤筋动骨的改动，一定先 /plan。这就是软件工程里「先设计再编码」，只不过设计稿由 AI 起草，你审批。

**/model 和 /effort —— 按活的大小分配火力。** /model 切换模型，/effort 调推理深度。我走的中转站按 token 计费，这条对我不是虚话：改文案、顺句子用便宜的；调 bug、做设计换重模型加 effort，钱花在刀刃上。

**/clear —— 换任务先清空。** 全文我最想强调的一条。上下文窗口有限，上个任务的讨论、报错、代码片段全堆在里面，新任务的信噪比就被拉低了，Claude 会拿着旧任务的假设来理解新任务。一个任务一个会话，干完 /clear，干净开始。

**/compact 和 /context —— 长对话的续命包。** 一个任务干太久，上下文快满，/compact 把之前的对话总结压缩、腾出空间；/context 能看到现在是什么占着窗口。注意压缩是有损的，细节会丢——重要结论先让 Claude 写进文件，再压缩。

## 发布前：让 Claude 自己过质量关

代码写完别急着发，这个环节 Claude 比大部分新手的自查靠谱。

**/diff** —— 先看这轮到底改了什么。Claude 动了一堆文件之后，自己过一遍 diff，再谈别的。

**/code-review** —— 审查当前 diff 找正确性 bug，加 --fix 可以让它顺手修掉发现的问题。提醒一句：网上不少老教程写的是 /review，现在它是 /code-review 的别名，功能一样。

**/security-review** —— 发布前查一遍安全漏洞：注入、鉴权、数据泄露。做产品的，这条在上线的分支上跑一次不亏。

## 出问题时：/rewind 是新手的后悔药

新手最怕「Claude 把我项目改坏了」。为这个，Claude Code 准备了三件工具。

![](assets/4.png)

**/rewind** —— 把代码和对话一起回滚到之前的检查点。Claude 每次改动前都自动存档，改坏了直接 /rewind，不用自己去翻 git。有这条兜底，我才敢放心让它大刀阔斧地干。

**/resume** —— 关掉终端，对话还在。会话是持久化的，第二天 /resume 打开选择器，挑一个接着干。

**/branch** —— 想试另一个方案又不想丢当前进度：从当前对话分叉出去，两边互不干扰，原路随时回来。

## 进阶：等你用熟了，写自己的 /命令

用了几天我发现，流程里有大量重复。比如我有个 100 天写作的仓库，每天发文都是固定几步：建文件夹、定角度、列大纲、收尾提交。每次口头交代一遍，Claude 能做，但我说得口干舌燥。

Claude Code 的解法是**自定义命令**：写一个 md 文件，把要说的话放进去，存到指定目录，它就变成一条 /命令。

这事我还有个现成的教训可以讲：我打 /daily 发现它只在写作仓库里有，换个目录就没了。查了才明白——项目级命令就是仓库里的 `.claude/commands/` 文件夹，跟 git 一起走，从哪启动 claude 就从哪找：

```text
你的项目/.claude/commands/daily.md    ← 项目级，只在项目里可用，随 git 提交
C:\Users\你\.claude\commands\xxx.md   ← 用户级，任何目录都可用
```

自己写一条也就十行。保存成 `C:\Users\你\.claude\commands\zh.md`，重启 Claude Code，任何目录输入 /zh 就能用：

```markdown
---
description: 把上一条回复用说人话的中文重讲一遍
---

把上一条回复翻译成说人话的中文，保留代码和英文术语原文。
```

文件名就是命令名，正文就是提示词模板，`$ARGUMENTS` 会被替换成命令后面跟的参数。frontmatter 里还能写 allowed-tools，限制这条命令允许用哪些工具。

我这个写作仓库里有三条：/daily 开稿、/publish 出公众号排版、/wrap 收尾提交。每天的文章就是用它们生产的——包括这一篇。

## 我踩到的坑

**坑一：在错误的目录启动，命令凭空消失。** 现象：打 /daily 提示不存在，但它昨天明明还在。原因：项目级命令是从「启动 claude 时所在的目录」往下找 `.claude/commands/` 的，我在别的文件夹启动了 claude，自然找不到。解决：在项目根目录启动；个人常用的命令放用户级目录。

**坑二：教程会过时，文档是唯一准绳。** 写这篇文章时我对照官方文档逐条核了一遍，发现网上老教程还在教的 /vim 已经移除，功能合并进 /config 的 Editor mode；/pr-comments 也移除了。Claude Code 迭代很快，遇到「教程说有但实际没有」的命令，直接查官方文档。

## 清单之外：我故意没写进来的命令

官方文档里大几十条，我实际用上的不到十五条。以下这些看着眼熟，但建议新手先别碰——不是不好，是时机未到：

- **/agents、/subtask、/fork、/batch** —— 多任务并行、批量改造代码库。等你有「同时让 Claude 干三件事」的需求再研究
- **/mcp** —— 给 Claude 接外部工具（浏览器、数据库）。做产品迟早要用，但先把基本循环跑顺
- **/deep-research、/schedule** —— 联网调研、定时任务，锦上添花
- **/usage** —— 看用量，/cost 和 /stats 都是它的别名，中转站用户偶尔看一眼有好处

另外有一批带场景名的命令——/design、/slides、/dataviz——作用是给特定任务加载专业参考资料，用到了 Claude 会自己调，不用背。

## 小结

1. 真正常用的就十来条，按四个阶段记：开工 /init，循环 /plan /clear，质量关 /code-review，救火 /rewind
2. 最值钱的不是命令本身，是 /clear 背后的习惯：一个任务一个干净上下文
3. 重复超过三次的流程，写成自己的 /命令——一个 md 文件而已，没有魔法
